# HTTP API v1 and event-driven operations

Approved architecture: the Mod is a JAR in the Minecraft server, a companion Docker container executes ZFS operations, and native TrueNAS replication copies published snapshots. Replace all shared-mailbox IPC with HTTP; no cron jobs, systemd services, file polling, Docker socket or host PID namespace. Keep existing world dataset names, mounts and published `mc-hourly-*` snapshot names compatible with native replication.

## Transport and configuration

The companion listens on port 8765 on a private Docker network shared with Crafty. Publish no host port. Every `/v1/` endpoint requires `Authorization: Bearer <token>`, constant-time checked. `/healthz` is unauthenticated and returns only readiness. Limit JSON requests to 16KiB, reject malformed JSON/duplicate keys/invalid scalar types, bound socket reads and request concurrency. Secrets and authorization headers must never enter logs. The token is at least32 characters, loaded from a regular file. Administrator configuration fixes one source dataset/world and, optionally, one Crafty URL/server ID; HTTP messages cannot choose host commands, paths, datasets or Crafty servers.

Agent configuration retains source_dataset, world_path, state_dir, keep24 and min_interval_seconds60; removes mailbox_path/poll_seconds. Add listen_host(default0.0.0.0), listen_port(default8765), api_token_file. Optional `crafty` object: base_url, server_id, token_file, verify_tls(defaulttrue), ca_file(optional), stop_timeout_seconds(default180), start_timeout_seconds(default180). A configured Crafty integration enables rollback and requires a writable world bind. Paths remain normalized administrator-owned configuration. Config/state remain root-owned, private, durable. Use a new HTTP state directory for the live migration, preserving the old ledger as evidence.

Mod properties: agent_url(defaulthttp://minecraft-zfs-agent:8765), agent_token_file(defaultconfig/local-zfs-backup.token), interval_seconds3600, freeze_timeout_seconds15, only_if_players_been_onlinetrue, snapshot_on_shutdowntrue. Remove bridge_directory. Use Java21 HttpClient with asynchronous requests and bounded daemon workers. Only completed callbacks marshalled onto the server thread may change game state; never wait on HTTP on a running server tick. There is no periodic HTTP heartbeat polling: readiness is checked by preparing each checkpoint. A bounded HTTP wait is permissible only after `ServerStoppedEvent`, when gameplay and world writes have ended.

## Checkpoint endpoints

All times are integer Unix epoch milliseconds, IDs canonical lowercase UUIDs. Replies include id,state,updated_ms and snapshot when allocated. JSON errors have error.code and error.message with no secrets. Use meaningful HTTP statuses (400 malformed,401 unauthorized,404 unknown,409 busy/conflict,410 expired,503 source unavailable). Duplicate requests are idempotent only if their original identity/event/timing matches. Freeze budget includes prepare/save barrier/snapshot response; failure restores flags and attempts CANCEL. Default failure backoff60s.

1. `POST /v1/checkpoints` body `{id,event,created_ms,deadline_ms}` prepares a checkpoint, preflights the mounted source, and returns PREPARED. Events: periodic_save,manual_save. No snapshot yet. Reject another active checkpoint/rollback. Client has not disabled saving before PREPARED.
2. On server thread the Mod captures all prior noSave flags, disables saving, forces flush and completes optional AsyncPlayerSave barrier asynchronously.
3. `POST /v1/checkpoints/{id}/snapshot` body `{frozen_ms}` requires the prepared original deadline and creates only a durable recorded pending snapshot. Recheck deadline after ZFS completes; return SNAPSHOT_READY only within it. frozen_ms is between created/deadline and not over1s future.
4. Mod restores all prior saving flags BEFORE `POST /v1/checkpoints/{id}/commit` body `{committed_ms}`. committed_ms must be within original created/deadline and at most1s future, received within deadline+60s. Rename to published only after valid matching commit; respond COMMITTED. Persist rename intent/GUID for restart reconciliation. Repeated commit cannot create another snapshot.
5. `POST /v1/checkpoints/{id}/cancel` body `{cancelled_ms}` removes only this operation's unpublished pending snapshot; never delete a committed one. Expired operation cleanup uses internal deadlines, not shared-file polling.

Reuse the proven safety rules: root-owned intent before ZFS mutation, immutable GUID checks, reconciliation after rename, orphan-owned-pending cleanup, non-forced/non-recursive local retention that respects real external holds, bounded completed history. Snapshot names keep the existing regex. Preserve event metadata in the durable operation record; old snapshots may have event unknown. Native replication excludes pending names.

`GET /v1/status` returns readiness, checkpoint state, last success/error and current/last rollback job. `GET /v1/snapshots` returns managed published snapshots with name,GUID and event when known. Snapshot listing never includes pending snapshots.

## Lifecycle and commands

`POST /v1/lifecycle` body `{id,event,created_ms,backup_requested}` records server_started or server_stopped. ServerStarted sends backup_requested=false. ServerStopped runs only after world save/close, with backup_requested determined by snapshot_on_shutdown and activity policy. Its bounded request may synchronously create/publish a shutdown recovery point because no game saving flags remain to restore. Always record the event; if rollback maintenance is active, skip snapshot creation and return a clear accepted/skipped response. A lifecycle event must not cancel or commit another checkpoint. Events have durable bounded deduplication.

Operator level4 commands: `/zfsbackup save` (forced save+checkpoint, alias now), status, list, `/zfsbackup rollback <snapshot>`, `/zfsbackup rollback status`. All HTTP is asynchronous while gameplay runs. Manual saves bypass the idle filter; successful COMMITTED clears only the activity generation captured at request start. Lifecycle shutdown snapshot honors activity, and failures preserve it. Stop handlers first cancel/restore an in-flight normal checkpoint. The adapter must verify the actual NeoForge ServerStopped hook ordering before relying on it.

## One-click rollback

`POST /v1/rollbacks` body `{id,snapshot}` returns202 with a durable background job; `GET /v1/rollbacks/{id}` and `/v1/rollbacks/current` expose status. An authenticated administrative `POST /v1/rollbacks/{id}/resume` with `{}` explicitly resumes the current FAILED job; it never retries automatically. This remains accessible while the game is stopped. Snapshot must be a managed published point of the fixed source dataset with a recorded GUID. Reject concurrent checkpoints/rollbacks. Normal checkpoints are blocked throughout maintenance. Duplicate job ID/snapshot returns the same job; changing it is409. Never run `zfs rollback -r`, destroy later snapshots, or switch a live Docker world mount.

Sequence: persist intent and hold selected point; save Crafty auto_start/crash_detection settings; PATCH bothfalse and verify; request orderly stop; wait for *fresh* Crafty stats (stats_id and created advance from the pre-stop baseline, running=false). Crafty timestamps are local naive datetimes, so compare their progression rather than assuming UTC. For a server already stopped, Crafty emits no fresh stop record: cached running=false is accepted only with verified disabled restart policies and the actual session lock described below. Persist the baseline for interrupted jobs. HTTP200 from stop is only queued, and online=false is insufficient. Additionally acquire Minecraft's actual `session.lock` using nonblocking POSIX record locking (`fcntl.lockf`, not flock), keeping that descriptor/inode locked throughout restoration. This prevents another JVM opening the world even if started unexpectedly. Never replace/delete/restore session.lock while holding it. Test lock compatibility with a real Java FileChannel lock.

After lock acquisition, create and durably record a pre_rollback recovery snapshot; preserve it on failures. Restore the selected immutable snapshot into the *existing* world dataset using safe block-cloning file copies, preserving metadata and symlinks, deleting extraneous world entries, excluding .zfs/session.lock. Use copy_file_range without an unbounded full-copy fallback to avoid filling the nearly-full pool. Do not follow untrusted destination symlinks or overwrite state/config outside world. Preserve source point/GUID and holds; fsync files/directories and persist job phase before changing data. Validate restored tree. Create a rollback_completed recovery point, release the world lock, start through Crafty, wait for fresh running/online readiness, then restore original automatic-start/crash policy and release successful-job holds. Failed restore/start leaves server stopped and automatic restart disabled, with progress/error and recovery snapshot retained. Do not automatically attempt another destructive rollback.

Persist enough intent/settings/source GUID/pre-recovery point/phase to resume an interrupted restore on container restart. Before any resumed write, disable auto-start/crash detection again, stop and re-verify offline/lock. Reapplying restoration from the immutable selected snapshot is idempotent. A pre-recovery point must not be replaced by a snapshot of a partially restored world. Keep active/failed-operation holds; prune neither selected nor recovery points while the job depends on them.

## Implementation boundaries

HTTP agent owner: agent config/protocol/coordinator/daemon/HTTP service, snapshot backend methods, Dockerfile/Compose example/agent docs and tests. Export a thread-safe checkpoint service with a maintenance gate. Rollback owner: new `crafty.py`, `restore.py`, `rollback.py` and matching tests; coordinate exact Python interfaces with HTTP owner before editing. Suggested `RollbackManager.submit(id,snapshot)`, get(id), current(), busy and lifecycle notification; inject fixed snapshot backend and clock. HTTP owner invokes these; rollback owner must not edit shared service/config files.

Mod owner: mod/ only; Java transport, lifecycle and commands/tests. Root: this contract, public root/deployment docs, live integration and isolated Crafty validation. No production rollback during tests: use disposable datasets and an independent Crafty instance. Do not leak credentials into Git or tool output.
